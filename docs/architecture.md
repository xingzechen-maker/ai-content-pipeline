# 架构与工程笔记

这份文档记录**为什么这么设计**，以及每个设计背后的真实坑。
如果你只想用，看README；如果你想改，这里是必要前提。

## 数据流

```
topics.txt          选题（可人工编辑）
    ↓  check_similar.py     ← 查重闸门（事前，1% 成本）
collisions.json     撞题清单
    ↓  replace_topics.py     ← 自动补换（全局串行去重）
topics_fixed.txt
    ↓  generate_articles.py  ← 正文生成
articles.json
    ↓  check_similar.py     ← 第二道闸门（事后）
    ↓  publisher/            ← 浏览器自动化
    ↓  archive.py            ← 归档
archive.docx
```

## 五个关键决策

### 1. 查重放在选题阶段，而不是成稿阶段

**理由**：撞题在选题时就已确定，成稿阶段才发现等于白花钱。

| 路径 | 成本 |
|---|---|
| 事后替换 | 白生成 21 篇正文 + 二次生成 + 二次查重 |
| 事前拦截 | 1 分钟选题检查 |

**代价**：选题阶段无法检查正文质量，只能查标题。所以保留事后那道作为兜底。

### 2. 禁用清单必须显式喂"考点"，不能只喂"已生成选题"

**理由**：模型看不见存量内容。

直觉写法是把已生成的30 条选题塞进 prompt。但撞车对象在存量里、模型看不到，于是反复吐回同一个熟考点。

**正确写法**：把撞车对象**及其原篇考点**作为红线喂进去，并明确"仅换措辞不算换"。

```
✗ 已生成选题：[…30条…]请避免重复
✓ 禁止再写以下考点：A（已用）、B（已用）、C（已用）
  要求：换一个完全不同的切入点，仅换措辞/语序不算换
```

### 3. 分组去重时，各组必须看到彼此的产出

**理由**：这是复检阶段才发现的坑。

首轮补换按类别分组，各自拿独立红线 → "痛点解决"和"学科备考"**各选了同一个考点** → 产出 2 篇撞自己人的内容。

**修法**：`accepted` 全局累积，每类采用的选题并入后续类别的禁用清单。

> 通用教训：并发/分组去重时，各分组必须看到彼此的产出。否则去重只在组内有效，组间必然相撞。

### 4. 敏感词用占位符保护专名，不用"最长键优先"

**理由**："最长键优先"看起来对，实测证伪。

字典里`大学生` 是 `大学` 的**前缀**，按长度降序排会让 `大学` 抢在前面替换、反而破坏 `大学生 → 高校生`。

- 长度策略对**后缀关系**有效
- 对**前缀关系**无效

正确解法：受保护子串 → 占位符 → 替换 → 还原。见 `lib/sanitize.py`。

### 5. 进度必须带批次指纹

**理由**：没有指纹的进度文件，连续四个批次各踩一次。

`nextIndex=200` + 新批只有 200 篇（索引 0–199）→ 从第 200 篇往后找 → **本批全部跳过**。

修复：指纹 `篇数:首-末` + 越界硬判据。见 `lib/progress.py`。

## 几个必须知道的工程现实

### 一轮补换清不干净，必须复检

实测（39 条撞题）：

```
轮次 1：≥0.85 归零，≥0.75 仍剩 3 条（撞的是本批自己）
轮次 2：0 → 3
轮次 3：→ 0/0
```

### 残留不应追到 0

要求 200 条标题与近 3000 条存量任意两条都不相像，**数学上不现实**。

阈值经验：
- `0.85` 必换（近乎同题）
- `0.75` 应换（同考点不同措辞，正文必然重叠）
- `0.70` 只作观察（多为不同考点的措辞接近，人工判断可接受）

### 思考模式下temperature 不生效

默认开启且 effort 默认为高，不显式关闭会显著增加 token 与耗时（实测小样本 prompt 11→37、输出 13→79）。

**且依赖 `temperature` 的场景必须关闭思考**——设置了不报错但不作用。

### 前缀缓存靠"prompt 保持完全一致"

同一段长 prompt 连续调用可命中缓存（实测命中率约 72%）。所以 `SYSTEM_PROMPT` 在整批中应保持完全一致。

### 分时计费能差出一倍

按百万tokens 计费，**空闲价 = 高峰价的一半**。批量任务值得调度到空闲时段。

### "提交超时"是「不确定」不是「失败」

请求可能已到达服务端并落库。**直接重发会产生重复内容。**

正确处置：先抓一次全量、按 ID 区间核对真实已发数量，只补发缺失部分。

## 排错口诀

| 症状 | 先看哪里 |
|---|---|
| `Target ... has been closed`、CDP 连不上 | **常驻进程日志**，别只盯发布日志 |
| 汇总 N 篇但实际少几篇 | 抓全量核对真实最大 ID；注意别用 `/成功/` 判成功 |
| 多篇失败提示弹窗内容完全相同、标题是别篇的 | 残留弹窗污染，见 `dismissDialogs` |
| 成功 0 篇 | 进度文件残留，看是否触发指纹/越界判据 |
| 崩在第 N 篇，后面全没发 | 单篇异常冒泡；确认主循环有 try/catch |
| 匹配不上外链 | 两端字典漂移，比对键顺序与取值 |
| 页面看着像列表页但实际已过期 | 唯一可靠检验是导航到受保护页面 |

## 不做什么

- **不做通用爬虫框架**：抓取上限、翻页策略各平台差异太大，抽象收益低。
- **不做多平台适配层**：每个平台的表单和审核机制差异超出可抽象范围。
- **不承诺通过率**：这套机制改善的是内容质量与流程可靠性，与平台判重结果无关。
