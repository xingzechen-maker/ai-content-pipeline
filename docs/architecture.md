# 架构与工程笔记

这份文档记录**为什么这么设计**，以及每个设计背后的真实坑。
如果你只想用，看README；如果你想改，这里是必要前提。

## 数据流

```
topics.txt          选题（可人工编辑）
    ↓  check_similar.py     ← 查重闸门（事前，1% 成本）
collisions.json     撞题清单
    ↓  replace_topics.py     ← 自动补换（全局串行去重）
topics_fixed.txt
    ↓  generate_articles.py  ← 正文生成
articles.json
    ↓  check_similar.py     ← 第二道闸门（事后）
    ↓  publisher/            ← 浏览器自动化
    ↓  archive.py            ← 归档
archive.docx
```

## 五个关键决策

### 1. 查重放在选题阶段，而不是成稿阶段

**理由**：撞题在选题时就已确定，成稿阶段才发现等于白花钱。

| 路径 | 成本 |
|---|---|
| 事后替换 | 白生成 21 篇正文 + 二次生成 + 二次查重 |
| 事前拦截 | 1 分钟选题检查 |

**代价**：选题阶段无法检查正文质量，只能查标题。所以保留事后那道作为兜底。

### 2. 禁用清单必须显式喂"考点"，不能只喂"已生成选题"

**理由**：模型看不见存量内容。

直觉写法是把已生成的30 条选题塞进 prompt。但撞车对象在存量里、模型看不到，于是反复吐回同一个熟考点。

**正确写法**：把撞车对象**及其原篇考点**作为红线喂进去，并明确"仅换措辞不算换"。

```
✗ 已生成选题：[…30条…]请避免重复
✓ 禁止再写以下考点：A（已用）、B（已用）、C（已用）
  要求：换一个完全不同的切入点，仅换措辞/语序不算换
```

### 3. 分组去重时，各组必须看到彼此的产出

**理由**：这是复检阶段才发现的坑。

首轮补换按类别分组，各自拿独立红线 → "痛点解决"和"学科备考"**各选了同一个考点** → 产出 2 篇撞自己人的内容。

**修法**：`accepted` 全局累积，每类采用的选题并入后续类别的禁用清单。

> 通用教训：并发/分组去重时，各分组必须看到彼此的产出。否则去重只在组内有效，组间必然相撞。

### 4. 敏感词用占位符保护专名，不用"最长键优先"

**理由**："最长键优先"看起来对，实测证伪。

字典里`大学生` 是 `大学` 的**前缀**，按长度降序排会让 `大学` 抢在前面替换、反而破坏 `大学生 → 高校生`。

- 长度策略对**后缀关系**有效
- 对**前缀关系**无效

正确解法：受保护子串 → 占位符 → 替换 → 还原。见 `lib/sanitize.py`。

### 5. 进度必须带批次指纹

**理由**：没有指纹的进度文件，连续四个批次各踩一次。

`nextIndex=200` + 新批只有 200 篇（索引 0–199）→ 从第 200 篇往后找 → **本批全部跳过**。

修复：指纹 `篇数:首-末` + 越界硬判据。见 `lib/progress.py`。

### 6. 多栏目下，"发布到哪里"必须显式逐篇判定

**理由**：单栏目时它是常数；多栏目时它变成逐篇决策，
而**判错不报错** —— 文章照样发布成功，故障要等到抓链阶段
才暴露成"外链一条都没匹配上"，报错点与病因点隔了一个环节。

两个必做的动作：

1. **逐篇比对并切栏目**。后台的"保存并继续"会清空表单但**保留发布上下文**，
   于是同一批里后续文章全部落进上一篇的栏目。见 `publisher/multi_column.js`。
2. **显式设模板**。模板预设在"栏目默认模板"上，跨栏目会跟着变，
   同一批文章混着不同模板 —— 同样不报错。

判定逻辑本身（关键词优先于类别）见 `lib/column_router.py`；
配套的抓取侧改造见 `lib/scrape_inventory.py`。

> **通用教训：静默故障比崩溃贵。** 单栏目时代，"发布成功"确实等于"发对了"。
> 一旦引入多值决策（栏目、模板），这个等式就断了 ——
> 必须为每个多值项配一个显式的、可校验的写入动作。

## 几个必须知道的工程现实

### 一轮补换清不干净，必须复检

实测（39 条撞题）：

```
轮次 1：≥0.85 归零，≥0.75 仍剩 3 条（撞的是本批自己）
轮次 2：0 → 3
轮次 3：→ 0/0
```

### 残留不应追到 0

要求 200 条标题与近 3000 条存量任意两条都不相像，**数学上不现实**。

阈值经验：
- `0.85` 必换（近乎同题）
- `0.75` 应换（同考点不同措辞，正文必然重叠）
- `0.70` 只作观察（多为不同考点的措辞接近，人工判断可接受）

### 思考模式下temperature 不生效

默认开启且 effort 默认为高，不显式关闭会显著增加 token 与耗时（实测小样本 prompt 11→37、输出 13→79）。

**且依赖 `temperature` 的场景必须关闭思考**——设置了不报错但不作用。

### 前缀缓存靠"prompt 保持完全一致"

同一段长 prompt 连续调用可命中缓存（实测命中率约 72%）。所以 `SYSTEM_PROMPT` 在整批中应保持完全一致。

### 分时计费能差出一倍

按百万tokens 计费，**空闲价 = 高峰价的一半**。批量任务值得调度到空闲时段。

### "提交超时"是「不确定」不是「失败」

请求可能已到达服务端并落库。**直接重发会产生重复内容。**

正确处置：先抓一次全量、按 ID 区间核对真实已发数量，只补发缺失部分。

### 发布范围变了，抓取范围必须同步变

改成多栏目发布后，如果存量抓取仍只抓原先那个栏目：

```
发布：全部成功，200/200，全绿
抓链：只抓到旧栏目的内容
匹配：一条都对不上
```

**报错点与病因点隔了一个环节**，看起来像匹配脚本坏了。
两处配置应当来自**同一份栏目表**，不要各自维护一份列表。
见 `lib/scrape_inventory.py`。

### 撞题基线必须是「合并后的全量」

曾把一次为省时间做的**限页抓取切片**直接当成下一批的基线，
导致基线比线上少一大截 —— 新选题和「基线里没有的老文章」撞题，查不出来，白发。

基线是**持续累积的资产**：抓取时翻完为止，每批发布后把新增条目并进去。

### 补换的收敛判据：不降反升就停手

撞题条数多、要补换好几轮时，**盯着相似度的走势**：

```
轮次 1：57 → 17
轮次 2：17 → 6
轮次 3：6 → 3，但相似度从 0.75 升到 0.94   ← 停手信号
```

相似度**不降反升**，说明模型已在给定类别内收敛到存量话题，
再刷轮次只是烧钱。此时该做的是**人工收口**（直接改写标题、同主题不同表述），
而不是继续调 prompt。

另一个相关事实：**补换脚本会忽略你在清单里指定的题目**，
把它当参考而非指令，自己按类别重挑。想精确锁题只能在出题后手改。

### 上游 API 拥塞的判据

批量任务卡在选题阶段不动，先分清是谁的问题：

| 探测 | 结论 |
|---|---|
| 同域名的轻量接口（如查余额）秒回 + 推理接口超时 | **服务端拥塞**，等即可 |
| 全部超时 / DNS 失败 | 本机网络或代理 |
| 推理接口返回 402 之类的状态码 | 账户/额度问题 |

客户端已有超时+重试，拥塞通常能自愈。
**别在没分清责任方之前改脚本** —— 实测一次"卡死"其实是服务端排队。

### 日志重定向到文件后不实时刷新

Python 的 `print` 在输出不是终端时是块缓冲。
把输出重定向到日志文件，进度提示会攒着不刷出来，
**看起来像卡死，实际在正常跑**。判断进度要看落盘产物数量，不是看日志。

### 报告进度是纪律，不是礼貌

长任务中途长时间不汇报，会被当成卡死（实测被问了一次"怎么卡住了"，
而当时已经跑到 180/200）。
**流水线有多个等待环节（登录、生成、发布），每个环节都要主动报当前进度。**

## 排错口诀

| 症状 | 先看哪里 |
|---|---|
| `Target ... has been closed`、CDP 连不上 | **常驻进程日志**，别只盯发布日志 |
| 汇总 N 篇但实际少几篇 | 抓全量核对真实最大 ID；注意别用 `/成功/` 判成功 |
| 多篇失败提示弹窗内容完全相同、标题是别篇的 | 残留弹窗污染，见 `dismissDialogs` |
| 成功 0 篇 | 进度文件残留，看是否触发指纹/越界判据 |
| 崩在第 N 篇，后面全没发 | 单篇异常冒泡；确认主循环有 try/catch |
| 匹配不上外链 | 两端字典漂移，比对键顺序与取值 |
| 页面看着像列表页但实际已过期 | 唯一可靠检验是导航到受保护页面 |
| **多栏目下外链一条都匹配不上，但发布全绿** | **抓取范围没跟上发布范围**，见 `scrape_inventory` |
| **文章进了错误的栏目** | 提交后表单重置但上下文保留，须逐篇显式切栏目 |
| 补换几轮后相似度不降反升 | 模型已收敛，人工收口，别再刷轮次 |
| 任务"卡住"但没报错 | 先看落盘产物数；日志缓冲 + 上游拥塞是常见原因 |
| 文档"少了一截" | **先解包数段落/超链接数**，区分文件损坏 vs 预览器截断 |

## 不做什么

- **不做通用爬虫框架**：抓取上限、翻页策略各平台差异太大，抽象收益低。
- **不做多平台适配层**：每个平台的表单和审核机制差异超出可抽象范围。
- **不承诺通过率**：这套机制改善的是内容质量与流程可靠性，与平台判重结果无关。

## 合规提醒

- `inventory.json`（存量快照）、生成内容、日志都可能含业务数据，**使用前请自行确认合规**。
- 密钥只从环境变量读取，**永不进仓库**。
- 自动化请遵守目标平台的服务条款与robots 协议。
