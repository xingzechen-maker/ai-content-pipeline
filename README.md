# ai-content-pipeline

用大模型 API 批量生产 SEO/GEO 内容的工程化流水线。

不是"一个调用 API 的demo"，而是**一套在生产环境跑过千篇量级内容、解决了批量生产中真实痛点的流水线**。

## 它解决什么问题

批量用 LLM 生产内容时，真正的难点从来不是"调通 API"，而是下面这些：

| 问题 | 本仓库的做法 |
|---|---|
| 生成上百篇时选题会撞车，且**随存量增长而恶化** | 两道查重闸门 + 事前拦下 + 自动补换 |
| 平台有敏感词审核，删掉会导致**句子断裂** | 受保护子串占位符 + 同义替换优先 + 自愈降级 |
| 发布时标题被改写，导致本地与线上标题**匹配失败** | 单一事实来源的字典 + 两端等价性校验 |
| 批量任务中断后重跑会**重复发布或全部跳过** | 批次指纹 + 越界检测 + 断点续传 |
| 一个弹窗残留会**污染后续所有篇目** | 提交前快照弹窗 + 判定时过滤陈旧弹窗 |
| 长上下文 prompt 重复发送**成本失控** | 利用前缀缓存 + 统计实际命中率 |

## 核心设计：为什么查重闸门是这个仓库最重要的部分

### 平台的判重是"字符串全等"，但SEO 内耗不是

平台判重看标题字符串是否完全相同。问题是：

```
「「入口流程怎么走？第一步先弄清规则」」   ← 本批
「「入口流程怎么走？第一步先弄清规则」吗」 ← 存量
```

**平台认为：不重复，放行。**

但两个页面在抢同一个搜索词，互相稀释权重 —— 这叫 **内容内耗（cannibalization）**。平台查不出来，因为它只比字符串。

实测数据（200 篇新内容 vs 存量 2182 条）：

| 阈值 | 命中篇数 | 平台判重 |
|---|---|---|
| ≥ 0.85（近乎同题） | 5 | 全部放行 |
| ≥ 0.75（同考点不同措辞） | 8 | 全部放行 |
| ≥ 0.70（措辞接近） | 17 | 全部放行 |

**平台一道都没拦住。** 而且这个数字会随存量增长而单调恶化 —— 存量越大，撞得越多。

### 把检查提到"写正文之前"

撞题在**选题阶段就已确定**，没必要等 200 篇正文都写完才发现。

| 路径 | 成本 |
|---|---|
| 事后替换 | 白生成 21 篇正文 + 二次生成 + 二次查重 |
| 事前拦截 | 1 分钟选题检查（约 1% 成本） |

### 自动补换：两个缺一不可的机制

撞题数多到几十篇时，人工写替换选题已不现实，必须自动化。

**机制一：禁用清单（banned）**

直觉做法是"把已生成的选题塞进 prompt 让模型避开"。**这不够。**

撞车对象在**线上存量**里，模型根本看不见这些内容，于是会反复吐回同一个熟考点（实测反复出现同一批数学知识点）。必须把「撞车对象 + 原篇考点」作为**红线**显式喂进 prompt，并强调"改说法、换语序都不算换"。

**机制二：全局串行去重（accepted 累积）**

首轮补换按类别分组注入红线，各组拿到的是**独立**清单、互不知情 → 实测「痛点解决」和「学科备考」各选了一个相同的考点，**产出 2 篇撞自己人的内容**。

> **通用教训：并发/分组去重时，各分组必须看到彼此的产出。否则去重只在组内有效，组间必然相撞。**

修法：每类采用的选题累积进 `accepted`，并入后续类别的禁用清单。

**实测效果**：三轮复检 `12/39 → 0/3 → 0/0`。

### 阈值怎么定

`0.85` = 必换，`0.75` = 应换，`0.70` 只作观察。

要求 200 篇标题与近 3000 篇存量的任意两篇都不相像，**数学上不现实**。0.75 是合理工程阈值。

## 核心设计：敏感词处理

### 删词会打断句子

很多平台的敏感词策略是**只删不换**。于是：

```
原句：成为「冲击高分段」的隐形门槛
删字：成为「段」的隐形门槛← 句子残废
```

**原则：能换词就不删词，句子完整性优先。**

### 「最长键优先」是个看起来对的错误做法

直觉：先替换更长的键，就能保住 `大学城`。

实测证伪：字典里 `大学生` 是 `大学` 的**前缀**，按长度降序排会让 `大学` 抢在前面替换，反而破坏 `大学生 → 高校生`。

- 长度策略对**后缀关系**（`大学` / `大学城`）有效
- 对**前缀关系**无效

### 正确的做法：受保护子串占位符

替换前先把受保护子串换成控制字符占位符，替换完成后再还原：

```
「滨江科技园」→  「滨江科技园\u00011\u0001园区」
替换阶段：只动裸露的「大学」
还原阶段： 「滨江科技园」                ✅ 专名毫发无损
                「重点大学」→「重点高校」✅ 该换的仍然换了
```

### 另一个反直觉的坑：词内拼接

```
原句：「冲击高分段」的隐形门槛     键「冲击高分」→「稳步提升成绩」
结果：「稳步提升成绩段」          ← 断句
```

替换键若出现在**更长的固定搭配内部**（词内拼接），必须为整个搭配单列键，且**置于短键之前**。

这与"最长键优先已证伪"不矛盾 —— 那条讲的是**前缀包含**，这条是**词内拼接**，成因不同。**字典排序要按具体冲突类型判断，不能一刀切。**

## 核心设计：批量任务的状态管理

批量脚本最大的坑是"中断后重跑"。

### 进度残留 → 整批跳过

进度文件记录 `nextIndex`。跑新一批时若没清旧文件，新批只有 200 篇（索引 0–199），脚本会从"第 200 篇"往后找 → **本批全部跳过，0 发布**。

这不是一个坑，是**四个批次连续踩了四次**。

### 修复：批次指纹

指纹 = `篇数:首序号-末序号`。批次间区间必然不同。

| 情况 | 行为 |
|---|---|
| 指纹不匹配 | 判定他批残留，从头开始 |
| `nextIndex > 篇数` | 判定越界，从头开始（覆盖旧格式，**不依赖指纹的硬判据**） |
| 旧格式无指纹、未越界 | 沿用进度 + 明确告警 |
| 指纹匹配、未越界 | 正常断点续传 |
| 显式重置开关 | 忽略进度，从头开始 |

两套判据**互补，缺一不可**：指纹可能"假匹配"（两个不同的补发子集恰好区间相同），越界是不依赖任何外部条件的硬判据。

## 核心设计：浏览器自动化的三个坑

### 一个弹窗污染后续所有篇目

某篇触发"标题重复"弹窗后弹窗未被关闭，后续每一篇判定结果时都会读到它。因为其文本含"重复"二字，**一个残留弹窗连续污染了 9 篇**。

三层修复：
1. 弹窗关闭增加文案型按钮点击 + 兜底强制移除残留弹窗层
2. **提交前先快照已有弹窗文本，判定时过滤陈旧弹窗**（根治误判）
3. 失败分支也执行弹窗清理，防止污染下一篇

### 单篇异常打死整批

发布循环没有 try/catch 时，任意未捕获异常会冒泡终止整个进程 —— 实测崩在第 45 篇，**第 45~100 篇一篇都没发**。

修复：
- 等待表单就绪时要等**所有**输入框（原实现只等标题框，而摘要框渲染更晚 → 必崩）
- 主循环对单篇包 try/catch → 降级为"跳过本篇"并重新导航

### 看似 A 崩了，其实是 B 死了

```
异常退出：Target page, context or browser has been closed
CDP 端口连不上了
```

真因：启动常驻浏览器的进程**自己没有注册 dialog 处理器**。Playwright 的规则是——没注册 `'dialog'` 监听器时会**自动 dismiss** 弹窗。于是同一个弹窗被两个 Playwright 客户端同时抢，常驻进程的自动处理发现"弹窗没了"→ 抛异常 → **未捕获 → 常驻进程退出 → 它启动的浏览器被一并带走**。

"看着像发布脚本崩，其实是启动器死了。"

修复两层：
- 给常驻进程注册 handler，阻止自动处理路径
- **常驻进程的唯一使命是"活着"**，任何异常都不该带走它 → 全局兜底

> **排错口诀**：发布脚本报 `Target ... has been closed` → 先去看常驻进程日志，别只盯发布日志。

## 成本控制

### 前缀缓存

同一段长 prompt 连续调用，第二次可命中缓存（实测命中率约 72%）。所以 `SYSTEM_PROMPT` 在整批中保持完全一致 → 输入成本几乎可忽略。

### 关闭思考模式

默认开启且 effort 默认为高，不显式关闭会显著增加 token 与耗时（实测小样本 prompt 11→37、输出 13→79）。

**关键**：思考模式下 `temperature` **不生效**（设置不报错但不作用）。依赖 `temperature` 的场景必须关闭思考。

### 分时计费

按"百万tokens"计费，**空闲价 = 高峰价的一半**。批次成本可以差出一倍，调度时值得注意。

## 使用

```bash
# 1. 生成选题（便宜、快）
python lib/generate_topics.py --count 200 --categories examples/topics.txt --out topics.txt

# 2. 查重闸门（事前拦下）
python lib/check_similar.py --topics-file topics.txt --inventory inventory.json --threshold 0.75

# 3. 自动补换撞题
python lib/replace_topics.py --plan collisions.json --topics-file topics.txt --inventory inventory.json

# 4. 生成正文
python lib/generate_articles.py --topics-file topics.txt --out articles.json

# 5. 归档
python lib/archive.py --articles articles.json --out archive.docx
```

## 安全

- **密钥永不进代码仓库**。只从环境变量读取，日志中只打印首 8 位 + 末 4 位。
- `inventory.json`（存量快照）、生成内容、日志都可能含业务数据，**请自行确认合规后再用于生产**。
- 本仓库的 `publisher/` 是通用浏览器自动化框架，**不含任何特定平台的接口实现**，接入具体系统需自行适配。
